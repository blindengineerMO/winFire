# WinFire Secure
Micro-Segmentation made easy. Why pay expensive vendors for zero trust when it can be done for free...

WinFire is a control plane for Windows Firewall policy authoring, inventory, verification, log review, and identity segmentation configuration. This repository is an early implementation, **not a completed enforcement product**.


### Multi-user control plane
- Owner/Admin/Policy Editor/Auditor role model with resource-scoped permissions per policy, node group, and credential.
- Team creation and membership management; user profiles with per-user theme and notification preferences.
- Argon2 password verification, optional TOTP login, JWT access tokens with rotating refresh tokens, immediate session revocation, login rate limiting and account lockout.
- Immutable security audit log of every action ("who changed what and when") for compliance and reporting.

### Credential vault
- Envelope encryption at rest; passwords are write-only after save and never returned to the UI.
- Local and domain credential types, private or team visibility, assignment to nodes or node groups, and priority-ordered candidate credentials per node.
- One-click credential test against a node before anything is applied.

### Windows compatibility

| Target OS | Agentless WinRM/LSA | Firewall policy and event collection | Optional agent |
|---|---|---|---|
| Windows 10/11, Server 2016+ | Current PowerShell/CIM/LSA path; live checked on Windows 11 and Server 2022 | NetSecurity/WFP path; live checks only on those two test hosts | Self-contained .NET 10 x64 package when signed and configured; Microsoft currently supports Windows 10 LTSC/Enterprise editions |
| Vista/7, Server 2008/2008 R2 | PowerShell 2 compatible sign-in, WMI facts, and native LSA path when WinRM is installed | Paged rule inventory and guarded policy apply through `HNetCfg.FwPolicy2`; WMI Security event reads are implemented but need a live older-OS test | Not supported by the .NET 10 agent |
| Windows XP SP2 / Server 2003 SP1 | PowerShell 2 compatible sign-in, basic WMI facts and native LSA read/change path when WMF 2/WinRM is installed; no XP test host is available | Read-only inventory of current-profile port and application exceptions; policy writes and event collection remain unsupported | Unavailable with the .NET 10 agent |

The [Windows Management Framework table](https://learn.microsoft.com/en-us/powershell/scripting/windows-powershell/wmf-overview?view=powershell-7.5) lists XP with WMF 2 only and as out of support. [Microsoft's current .NET table](https://learn.microsoft.com/en-us/dotnet/core/install/windows) lists Windows 10 LTSC/Enterprise, Windows 11 and Server 2016+ for .NET 10, but not XP. The older-host firewall adapter has mock rollback tests and a live add/update/remove canary using the same COM API on Server 2022. Verify the PowerShell 2 paths against isolated older Windows VMs before relying on them. XP exposes only current-profile exceptions through its older firewall API; it cannot represent WinFire's outbound deny, per-rule profile, and account-scoped policies. Full XP firewall management remains an open plan item.

### Node inventory and agentless management
- Discover and onboard nodes by IP/FQDN; probe authenticated WinRMS, WinRM, then RPC/WMI, including the case where a WinRM port accepts TCP but rejects the supplied credentials; agentless and agent connection modes per node.
- Live collection of host facts (OS version/build, machine model/serial, firewall service status), forward and reverse DNS lookups, and management port probes.
- Remote, agentless firewall rule management (push desired state, read live state) with connection health checks, retries, and unreachable-node alerting.
- Windows 10/11 and Server 2016+ use the NetSecurity, CIM and Security log PowerShell surfaces. XP and Server 2003 have a read-only current-profile exception adapter; writes remain unavailable.

### Policy authoring and version control
- Visual drag-and-drop policy builder: allow/deny rules, port/program groups, remote-address groups, profile scopes, schedule windows, and MFA gate nodes wired into a rule precedence graph.
- Compile the graph into concrete firewall rules, tagged and scoped per policy so apply/rollback is safe and reconciliation never touches unrelated rules.
- Conflict detection when two assigned policies contradict on the same node.
- Immutable, versioned policy snapshots: review diffs and recall a prior version. Changes to enforced nodes remain staged until an administrator uses **Sync policies** in the top bar, immediately or at a scheduled change time.
- Visual graph and classic form/table editors. Compilation merges duplicate match conditions and compatible local ports before deployment.
- Draft buffer so in-progress edits survive a refresh without polluting version history.
- Audited apply runs showing the rule diff, per-node result, and error detail.

### Policy verification
- TCP-based allow and deny checks against assigned policies, with explicit pass/fail/inconclusive evidence. A deny passes only when the managed rule is present, the connection did not open, and a same-node Windows Filtering Platform 5157 block event matches the probe's source IP, source port, destination port, and [Filter Origin rule ID](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/filter-origin-documentation). Agentless checks capture the target's Security log record ID before probing, so host clock skew does not hide evidence. The verifier stores the event record ID, filter origin, and probe endpoint. A different origin or no matching event is inconclusive. A live ORLANDO test matched event 247032 to a temporary rule scoped to HOUSTON, passed verification, and read back the rule as absent after cleanup.
- On-demand "verify now" per policy or node plus scheduled sweeps; results feed drift detection and the compliance dashboard.

### Reporting
- Node inventory, DNS (forward/reverse with mismatch flags), policy coverage, verifier results, trending dashboards, and compliance reports.
- CSV and PDF export for audit hand-off.

### Firewall logs and learning mode
- Firewall and logon event collection from managed nodes with server-side pagination (100 events per page by default), sortable table columns, and filters for node, event ID, action, direction, source and destination IP, port, program, protocol, challenge ID, and time range.
- Administrators can select individual events across pages and send up to 500 at once to a configured syslog-over-TLS or Splunk HEC destination. Administration → Logs and DNS stores the destination and an encrypted HEC token; each export attempt and result is audited. TLS certificate validation is required, and export leaves local events intact.
- Modern Windows WFP events retain their source and destination order. Older event layouts are normalized separately. A database migration repairs previously reversed, uncompressed inbound records when collected node facts identify the local IP; new collections also fill missing Filter Origin values on duplicate records.
- Learning sessions: capture observed traffic during a window, auto-propose a least-privilege policy, hand it to an operator for review and approval, then apply and enforce.
- Agent learning proposals preserve a valid absolute Windows program path as a process-scoped firewall rule. Events whose process path cannot be validated still produce network-scoped proposals for operator review; device-path conversion and full 5-tuple process correlation remain open.
- New nodes start automatic training for 30 days by default. Each node gets one personal learned policy as soon as training starts. Policy Studio shows its live proposed graph and rules without saving a version for every observed event. Open a proposed rule's evidence to see event and source-port counts, the time window, the observed process, and up to five source/destination 5-tuple samples. The preview groups these tuples into deduplicated firewall rules; refreshed evidence is saved with progressive versions without reapplying unchanged rules. The Windows agent converts WFP device application paths to drive-letter paths before shipment when a local drive mapping exists. An unmapped process path remains in evidence; its proposal uses **Any program** and the Policy Studio marks that broader scope for review. At the deadline, WinFire checks telemetry, saves a final version, and applies the personal policy together with policies assigned directly, through ordinary groups, or through the built-in **All nodes (global)** group. The policy then stops learning; later changes require a manual version. Agent nodes become enforced after apply jobs are acknowledged. Relearning reuses the same personal policy and keeps prior rules active. Manual review sessions remain available in Event logs.
- Administration can enable progressive learning for new automatic sessions. It is off by default; the initial apply defaults to day 15 and later updates to every 24 hours until training ends. Each changed snapshot is an immutable policy version. The first apply day, update interval, and overall training duration are configurable. Existing sessions retain their schedule.
- Inventory shows each node's training state, AD identity, domain join state, DNS suffixes, OS and hardware details, current and last logged-on users, network adapters, firewall profiles, and paged live firewall rules. A background sweep collects WinRM facts for new agentless nodes after a credential is assigned; operators can refresh facts from the node detail view.
- On an agentless machine with RPC/WMI but no authenticated WinRM, onboarding checks the WMI computer name and tries to start PowerShell remoting. If WinRM activation fails, it can collect host facts, verify or enable Filtering Platform Connection auditing, and collect events over WMI instead. AD-discovered machines prefer the Directory WinRM credential; manually added machines use their assigned credentials. The new-node sweep does this automatically. HOUSTON (Server 2022) passed a WMI fact and audit-policy read; ORLANDO (Windows 11) completed WMI-to-WinRM promotion in the test domain. A live WMI-only onboarding remains unverified. [Microsoft documents](https://learn.microsoft.com/en-us/windows/win32/wmisdk/creating-processes-remotely) that remote WMI process creation is noninteractive and requires WMI Execute Method and Remote Enable permissions. Group Policy or firewall settings can still prevent activation.
- A WMI-authenticated host without WinRM can read host facts and paged firewall rules, apply managed policy diffs, manage firewall connection auditing, and collect Security events on Vista/Server 2008 or newer. This uses authenticated WMI process creation and the ADMIN$ SMB share to stage a short-lived PowerShell script, read its result, and remove temporary files. Host-local rollback and a fresh control-plane readback protect rule changes; an ambiguous write is not retried blindly. A live HOUSTON read returned 341 rules and 600 recent events, and a loopback-only WMI policy canary was added, updated, and removed with zero rules remaining. A live audit-policy change remains unverified.
- Policy apply, managed rule reads, drift checks, and verification use a common firewall connector interface. WinRM and WMI connectors return host readback immediately; the agent connector queues apply/read jobs and records their acknowledgements when the agent reports back.
- Admins can right-click an unenrolled WinRM node and choose **Deploy signed agent**. WinFire downloads a configured signed package to the node over HTTPS, checks its SHA-256 and Authenticode signature, enrolls it with a short-lived token, and creates an automatic Windows service. `AGENT_PACKAGE_PATH`, HTTPS `PUBLIC_BASE_URL`, trusted server TLS and agent PKI must be configured; this path has not yet been validated with a signed binary on Windows. Manual token enrollment remains available. The agent is optional for the existing WinRM policy, inventory and MFA paths.
- Admins can right-click a WinRM or enrolled-agent node and choose **Break glass**. A reason, 5–240 minute duration, and typed confirmation are required. The host snapshots Domain, Private, and Public firewall profile states, schedules a SYSTEM rollback task locally, then temporarily disables the profiles; explicit block rules would otherwise override allow-all rules. The control plane can restore early and sweeps expired sessions. Activation and restoration create audited apply runs; agent runs close after job readback. A reachable Windows host with permission to manage its firewall and Scheduled Tasks is required. The script has automated mock PowerShell coverage; host execution should be validated in a safe Windows test environment before operational use.
- Operators can edit manually added nodes in Inventory. Changing a management address clears stale WinRM facts and refreshes DNS; the API blocks address changes while policies are assigned. Admins can remove a manually added node after confirming its name, provided it has no active agent, identity segment, or policy assignment. Directory-managed computers must be removed from the AD discovery scope instead. Historical logs and audit records remain available after inventory removal.
- Administration → Directory configures an LDAPS domain controller, search base, vault bind credential, WinRM credential for discovered computers, and sync interval. An admin can test the bind and run a sync immediately. AD computer GUIDs anchor inventory across renames; missing computers are marked, and existing nodes and policies are retained. Enabled discovered computers start new-host training. WinFire resolves each computer name to an IP and uses the Directory WinRM credential. AD-discovered and manually added agentless computers both collect host facts, enable Filtering Platform Connection auditing when needed, and start the event collector automatically. Failures are audited and retried; the node is not marked fully onboarded until an authenticated WinRM or WMI connector returns facts, audit-policy readback, and an initial event pull. Entities → Directory inventories AD users with server-side search, sorting, filters and pages, shows MFA and Windows logon/logoff activity, and lets an admin import an enabled AD user as a dashboard operator. Imported operators authenticate with their AD credentials over LDAPS; disabled or missing AD users lose portal access. An admin can set a separate delegated account-control credential, then enable or disable a user with typed confirmation and an audited reason. A temporary disable can expire automatically; WinFire restores access only when AD flags still match its change, otherwise it flags the hold for manual review. These writes require LDAPS and have mock coverage, but have not been validated against a live writable AD tenant. Privileged-access policies remain planned.
- Entities → Directory also inventories local SAM users from agentless WinRM nodes. Use the **Source** filter to show AD or Local accounts, or **Refresh local accounts** to recollect a node. Local entries include their node-qualified username, SID, enabled and lockout status, password requirement, description, and node-specific logon events. Fact collection refreshes the local catalog automatically; a new unresolved event SID triggers a throttled WinRM lookup on its node. Domain controllers do not have local SAM users. Identity → Logon rights baseline and Firewall events resolve each SID against AD, then that node's local catalog, then Windows SID translation and well-known principal labels. Unresolved SIDs remain visible.
- From a local account's Directory detail, an administrator can stage an outbound reject rule for a destination IP/CIDR and port in that node's personal policy. The account SID is retained in Policy Studio and the compiled rule; **Sync policies** deploys it after the change review. Deployment verifies that the SID still belongs to the source node and reads the Windows firewall security filter back. This uses the Windows NetSecurity `LocalUser` condition on the source host. It cannot identify an unauthenticated remote local account from an inbound packet on a different host; enforce that case on the source node or use an authenticated identity control. Windows XP has no NetSecurity adapter for this rule type. A reserved-destination canary was applied, read back, and removed on the ORLANDO Windows 11 test workstation.
- Administration → Security includes automated response policies. An administrator can preview and enable a destination IP/known inventory hostname trigger or a repeated failed-MFA threshold, set its observation window and per-subject cooldown, and review incidents. Alerts use the existing in-app, email, and webhook notification preferences. A recent outbound event on a WinRM-managed source host can verify the live process owner SID and process creation time before temporarily disabling the matching AD user via the separate LDAPS action credential; the existing account hold controls re-enable. An optional combined action rechecks the active user session and logs it off with `WTSLogoffSession`. Inbound events, stale or missing processes, and missing credentials produce review alerts; a failed logoff produces a partial incident while the AD hold remains. Repeated authenticator-code failures can also temporarily disable the verified AD user after an authenticated AD session or successful LDAPS password bind has linked the challenge to the user's directory SID. Submitted usernames, AD password failures, Entra cancellations, and local operators never qualify for that action. Live writable AD and client logoff validation remain pending.
- Retention and pruning policies for stored events.

### Identity segmentation and MFA
- Segment definitions target a node or node group, port, source, account SID, and grant TTL. An administrator assigns operator emails, chooses TOTP or Entra ID, and can link a firewall policy. A linked policy must be assigned and its current version successfully synced to the target before portal access is granted. Challenge decisions and grants are recorded and audited.
- Logon-rights baseline reading and single-right changes for agentless WinRM nodes through the Windows LSA API (direct user and group SID assignments for remote interactive, network, interactive, batch, and service logon). In Identity → Logon rights baseline, an administrator can collect the current assignments or choose **Change logon right** to add or remove one assignment by SID. The change requires a reason and typed confirmation, protects critical system and administrator SIDs, verifies the result on the host, attempts rollback on a readback mismatch, and records an audited apply run. Direct removal of `SeNetworkLogonRight` and assignment of `SeDenyNetworkLogonRight` are blocked because they could lock out WinRM administration. The WinRM credential needs local policy administration privileges. Group Policy may overwrite local assignments; group membership and deny precedence are not expanded into an effective per-user decision. See [Microsoft's LSA enumeration contract](https://learn.microsoft.com/en-us/windows/win32/api/ntsecapi/nf-ntsecapi-lsaenumerateaccountswithuserright) and [account-rights API](https://learn.microsoft.com/en-us/windows/win32/api/ntsecapi/nf-ntsecapi-lsaaddaccountrights).
- Identity → Identity learning preview summarizes the last 30 days of Windows 4624/4625 logons by node, SID, logon type, and source IP. Successful account logons produce grouped suggestions for the corresponding LSA right; failed-only attempts do not suggest access. The screen shows whether a collected baseline has a direct allow or deny for that SID and right. Administrators can collect the baseline and open the confirmed right-change form from a suggestion. Group Policy, group membership, and deny precedence still require human review; the suggestions do not change rights automatically.
- The agentless **WinFire access portal** takes a fresh authenticator code or a fresh Entra sign-in, checks that the target's effective firewall profiles are enabled with inbound default Block and no other enabled allow rule for any configured TCP port, then adds one source-IP-scoped temporary allow rule covering the primary and extra ports. It confirms the port and source IP scope from the Windows firewall readback and records an apply run. A SYSTEM scheduled task on the Windows host removes the rule at expiry even if the control plane is offline; the control plane also retries expiry cleanup. Users can close their grant early. TOTP codes are single-use for portal grants. Every started TOTP, Entra, or manual challenge records its user, target, source, provider, time, and final result; Identity offers paginated challenge filters. Abandoned challenges expire automatically. Account SID, source process, and logged-on-user fallback settings cannot yet be enforced by the agentless portal, so a segment using any of them is refused instead of opening an unscoped grant. Entra requires a tenant app configured to emit the `amr` ID-token claim and an MFA Conditional Access policy; it has not been validated against a live tenant.
- Manual and scheduled MFA grant removal confirm Windows readback and record an apply run. A failed removal leaves the grant pending for retry.
- Administration → Branding sets the company name and uploads a validated PNG, JPEG, or WebP image for the MFA page and its prompted login. An administrator can opt a segment into automatic browser prompts. A short interval collector matches inbound blocked 5157 traffic to a managed or AD discovered workstation, then matches a recent outbound 5156 TCP event, source port, process owner, and active session on that workstation. A one-time interactive Scheduled Task opens a dedicated, short-lived `/mfa/<request-id>` page for that user. The page shows the protected host, source workstation, session, program when available, and the required sign-in action. Microsoft sign-in redirects to the configured Entra tenant; the AD + Google Authenticator action asks for an AD password over LDAPS and a single-use TOTP code from the operator's enrolled authenticator. The prompt does not require a separate WinFire dashboard login, but the verified email must belong to an enabled, assigned WinFire operator. AD discovered clients use the Directory WinRM credential when no node credential is assigned; newly discovered names can be resolved before their scheduled DNS refresh. Disconnected sessions, duplicate inventory IPs, and ambiguous process ownership remain blocked. Administration → Branding also controls an explicit, default-off fail-open fallback for unknown or WinRM-unreachable clients. Enabling it requires typed approval and creates a 2–15 minute audited source-IP grant without MFA; the target firewall preflight must still pass. See [the Microsoft-based design notes](RESEARCH_AGENTLESS_MFA.md).
- Policy version and apply guards reject rules that would block inbound WinRM or known WinFire control-plane traffic. Set `WINFIRE_CONTROL_PLANE_IPS` to every deployment address, including NAT or load-balancer addresses.
- The portal opens network access before the user retries RDP or SSH. The optional browser prompt reacts to a blocked event after polling; it cannot intercept or resume the original connection. Portal approval does not yet change Windows logon rights automatically. Agent connection interception and automated logon-rights JIT remain under development.

### Agent distribution and remote enforcement
- Short-lived enrollment tokens, an operator-run PowerShell service installer for a separately signed agent executable, certificate-based node identity, and polling for policy jobs. Remote agent installation records an audited apply run with the package hash and confirmed enrollment/service result. A signed MSI, hosted download/bootstrap flow, agent push channel, and self-update remain planned.
- Secure remote access posture: per-node certificates, short-lived rotation, fail-closed MFA defaults with an explicit audited break-glass override.

### Platform behavior
- Single-port deployment (API and UI) with strict CORS; everything behind one reverse-proxy-terminated TLS origin.
- Scheduled background jobs (verifier sweeps, event collection, learning timers) with configurable intervals.
- Data persisted to a versioned database with an encryption-key file; the record store is excluded from source control.

## Run

Requires Node.js 20.19+ or 22.12+ (Node 24 recommended) and npm 11+.

```bash
npm ci
npm start
```

`npm start` builds the Vue app, starts Express, serves the UI and `/api/v1` on the same `PORT` (default 3000), and creates `data/winfire.db` and `data/secrets.json` on a local first run. Knex applies schema migrations before the API listens. The first run prints a random owner password to the terminal. To choose credentials, set `BOOTSTRAP_EMAIL` and `BOOTSTRAP_PASSWORD` before the first start. Keep the local `data/secrets.json` backed up and private: losing it makes encrypted vault records and existing refresh tokens unusable. Production (`NODE_ENV=production`) requires `JWT_SECRET` and `VAULT_MASTER_KEY` supplied by the deployment secret store and does not create or read `secrets.json`. The data directory is ignored by Git.

`/api/v1/openapi.json` enumerates the registered control-plane and agent routes, path parameters, and bearer-token or agent-certificate security. Login and refresh requests have typed schemas; the other request and response bodies currently use generic schemas pending per-route schema extraction.

For a local demo, `npm start` also ensures an admin account at **`admin@winfire.local` / `WinFireDemo!2026`**. Its password is stable on every startup. Set `BOOTSTRAP_ADMIN_EMAIL` and `BOOTSTRAP_ADMIN_PASSWORD` to change the credentials; startup updates the same marked account and revokes its existing sessions when they change. Set `BOOTSTRAP_ADMIN_ENABLED=false` to suspend it. The account is disabled by default when `NODE_ENV=production` unless `BOOTSTRAP_ADMIN_ENABLED=true` is set explicitly. Do not enable a known demo password on a public deployment. `.env.example` documents the variables; export them in the shell or deployment environment because `npm start` does not automatically load that file.

For development, use `npm run dev:api` and `npm run dev:web` in separate terminals; Vite proxies `/api` to Express. Run `npm test` and `npm run build` before deployment.

### Configuration

Copy [.env.example](.env.example) into your deployment configuration and export the values before starting; Node does not automatically read `.env` here. Set `PORT`/`HOST` for the single Express listener and `DATA_DIR` for the SQLite database. Production requires a random `JWT_SECRET` of at least 32 characters and a base64 32-byte `VAULT_MASTER_KEY` from an external secret store, plus unique bootstrap passwords. `BOOTSTRAP_ADMIN_*` controls the stable demo operator; disable it in production unless explicitly needed. `CORS_ORIGIN` is only needed for a separate UI origin. Use `TLS_CERT`, `TLS_KEY`, and the agent CA settings together if enrolling agents. In production both private keys must be encrypted PKCS#8 files, with `TLS_KEY_PASSPHRASE` and `AGENT_CA_PASSPHRASE` supplied separately. `SMTP_*` and `PUBLIC_BASE_URL` enable invitation and verification mail; `NOTIFICATION_WEBHOOK_URL` enables outbound alerts. `LOG_RETENTION_DAYS`, `SWEEP_INTERVAL_MINUTES`, and `AUTH_RATE_LIMIT` set the starting maintenance and login limits. The Logs & DNS screen controls the event compaction interval, loopback display/ingest behavior, and DNS refresh interval at runtime.

To enable one-click agent deployment, publish and Authenticode-sign the self-contained `WinFire.Agent.exe`, set `AGENT_PACKAGE_PATH` to that signed file, and set `PUBLIC_BASE_URL` to the trusted HTTPS origin reachable from Windows nodes. Configure the server and agent CA certificates below. The node's assigned WinRM credential must have local administrator rights. WinFire verifies the download hash and the Windows signature before creating the service; an unsigned file is rejected on the host.

For portal MFA behind a reverse proxy, set `TRUST_PROXY_CIDRS` to **only** the proxy's trusted address or CIDR; WinFire uses the resulting browser IP as the temporary rule's source. Serve the portal over HTTPS and ensure the browser's source IP is the one Windows Firewall will see when the user connects. Automatic browser prompts additionally require an HTTPS `PUBLIC_BASE_URL`, WinRM credentials on the source and target, WFP failure auditing on the target, and success auditing on the source. They are off per segment until enabled in Identity. `MFA_EVENT_POLL_SECONDS` sets the poll interval (30 seconds by default). The firewall gate must have enabled profiles with inbound default Block and no other enabled inbound allow or block rule for the protected TCP port. Granting access to an already open or explicitly blocked port is refused. Fail-open fallback is a deliberate MFA bypass for uncontrolled clients and is off by default; use Administration → Branding to enable it with typed approval and a short duration. For the prompted AD + Google Authenticator flow, configure a certificate-validating LDAPS connection in Administration → Directory, list the operator's email in the segment, and have that operator enroll an authenticator under Administration → Security. Approved LDAP 389 fallback applies only to directory inventory and never to interactive password authentication. For Entra, configure the tenant ID, client ID, and write-only client secret in Administration → Entra, or set `ENTRA_TENANT_ID`, `ENTRA_CLIENT_ID`, and `ENTRA_CLIENT_SECRET` as environment variables. Saved settings take precedence and encrypt the secret with the vault master key. Set an HTTPS `PUBLIC_BASE_URL`; register both `https://<your-host>/identity` and `https://<your-host>/mfa/callback` as web redirect URIs, add `amr` as an optional **ID token** claim, and require MFA for the app with Conditional Access. WinFire requires `mfa` in the validated ID token, the configured tenant, and an email matching an enabled, assigned WinFire operator. Use a tenant-specific app and secret manager for the client secret. See [Microsoft's OIDC setup](https://learn.microsoft.com/en-us/entra/identity-platform/v2-protocols-oidc) and [optional claims guidance](https://learn.microsoft.com/en-us/entra/identity-platform/optional-claims). The Entra path still needs live tenant validation and Entra group targeting is not implemented.

### First-run workflow

For AD + Google Authenticator, share `https://<your-host>/enroll-authenticator` with users or direct them to **Enroll Authenticator** on the main sign-in page or MFA prompt. They sign in with their AD UPN and password over certificate-validated LDAPS, scan the QR code with Google Authenticator or another TOTP app, and confirm a current six-digit code. The setup token expires after 10 minutes and cannot be reused; the TOTP secret is encrypted at rest. Newly enrolled AD users can approve assigned MFA prompts without a dashboard account. Their AD enrollment does not create a dashboard password. Existing dashboard users enroll under Administration → Security. Authenticator recovery for an already enrolled AD user requires administrator assistance. Production enrollment requires HTTPS, including a correctly configured trusted proxy if TLS ends there. LDAP 389 fallback is never used for user sign-in or enrollment.

1. Sign in with the bootstrap owner or configured demo admin, then create named operators and grant only the permissions they need in Administration.
2. Add a directory bind account and WinRM account to the Credential vault. In Administration → Directory, configure the controller URL and search base, test the connection, then run a computer sync. LDAP 389 fallback requires an administrator's explicit approval. Alternatively, add a node manually in Monitored assets.
3. For manually added agentless nodes, assign a credential to the node or group. AD discovered nodes use the Directory WinRM credential. Both onboard automatically. Open a node to inspect collected identity, OS, network, DNS, firewall, and training details. New nodes enter automatic training. Check the audit trail for `node.onboarding.failed` if host facts or firewall events do not appear; the error identifies an unreachable WinRM endpoint or auditing failure.
4. Review each personal learned policy in Policy Studio. Use the graph or Classic rules editor for manual policies, assign them to nodes or groups, and inspect conflicts and version diffs. For enforced nodes, use **Sync policies** in the top bar to deploy now or schedule a change window. Training sessions follow their configured timeline.
5. In Firewall Events, search and sort traffic, right-click a flow to stage an allow or reject rule, and use the loopback toggle when troubleshooting. In Inventory, click a group to inspect members. Use Reports and the Administration audit trail to review and export evidence.
6. For portal access, create an agentless Identity segment for one node or group, select TCP 3389 or 22, list permitted operator emails, choose TOTP or Entra, and set a short TTL. Link an assigned firewall policy if the grant should depend on its synced version. Administration → Branding sets the company name and image. Enable the segment's automatic browser prompt only after the source workstation and audit prerequisites are ready. Remove other enabled allow rules for that port from the target and verify its inbound profile defaults are Block. The operator opens Identity or follows the prompted browser page, completes MFA, and then retries RDP or SSH. The Active grants list shows expiry and offers early revocation.

### Storage limits

The application currently runs on SQLite through a synchronous `better-sqlite3` data layer. The event pattern dictionary reduces repeated payload storage, but there is no PostgreSQL runtime or in-app migration wizard yet. Do not plan a multi-replica deployment against the SQLite file. Back up both the database and `data/secrets.json`; restore them together. See [IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md) for remaining work.

On Linux, run `npm run setup:winrm` once to install the Python WSMan and DCOM/WMI transports in `.venv`. The Docker image includes both and `rpcclient`. On Windows, the connector uses PowerShell remoting for modern WinRM operations and Windows PowerShell for the WMI credential probe. The Python WSMan sidecar is required for authenticated WinRM probes and PowerShell 2 targets, and the Python WMI sidecar is required for WMI firewall operations; install their requirements and set `WINRM_PYTHON` and `WMI_PROBE_PYTHON` to that Python executable if needed. The Python transports use [pywinrm](https://github.com/diyan/pywinrm) and [Impacket's WMI interface](https://github.com/fortra/impacket/blob/master/examples/wmiquery.py). WMI firewall operations require both DCOM/RPC access and ADMIN$ SMB access with a credential permitted to manage firewall rules on the host. [Microsoft does not support WSMan remoting from current non-Windows PowerShell](https://learn.microsoft.com/en-us/powershell/scripting/security/remoting/wsman-remoting-in-powershell).

## Current capabilities

- Owner bootstrap, Argon2 password verification, optional TOTP login, JWT access tokens, rotating refresh tokens, immediate session revocation after password changes or admin action, protected owner role, invitations, role gates, login rate limits and account lockout.
- Administration → Access manages audited read and write grants for policies, node groups, and credential metadata. Owner, admin, editor, and auditor role gates resolve through database role permissions. Policy and group lists respect resource grants; credential use and rotation require write access, while a read grant reveals metadata only.
- Envelope encrypted credential records with write-only passwords; node inventory, DNS lookups and connection port probes.
- The Credential vault UI can attach a stored credential to an existing node or group, run a read-only authentication test against an assigned WinRM node, and rotate its write-only password. Assignment validates the target and treats a repeat request as already assigned.
- LDAPS computer discovery with scheduled and manual sync, AD GUID/SID and account status in inventory, and automatic WinRM fact collection for credentialed new nodes. AD test/sync requires an LDAPS endpoint with a certificate trusted by the control plane and a vault credential with directory read access.

For Active Directory discovery, the domain controller needs an LDAPS certificate with a private key, Server Authentication usage, and a DNS name matching the configured URL. Install it in the Local Computer or NTDS Personal store, and trust its issuing CA on the control plane (for example through `NODE_EXTRA_CA_CERTS`). The control plane keeps certificate verification enabled and reports DNS, connection, certificate, and bind failures in Administration → Directory. See [Microsoft's LDAPS certificate requirements](https://learn.microsoft.com/en-us/troubleshoot/windows-server/active-directory/enable-ldap-over-ssl-3rd-certification-authority).

Administration → Directory also offers an optional LDAP 389 fallback. It is **off by default**. An administrator must type `ALLOW LDAP 389` to approve that server and bind credential; changing the server or selected credential, or changing the selected credential's username or password, requires fresh approval. The fallback is attempted only when the LDAPS connection or handshake is unavailable, never when certificate validation fails or a completed bind/search fails. LDAP 389 uses a simple bind and sends the credential without TLS, so use a dedicated read-only directory account on a trusted network. Every approval, revocation and fallback sync is audited. A domain controller requiring LDAP signing will reject this cleartext bind; in that case configure LDAPS instead. See [Microsoft's LDAP signing behavior](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/ldap-signing).
- Account profile avatars stored outside the database with PNG, JPEG and WebP signature and size checks.
- Account notification preferences by event and channel, a personal in-app inbox, and queued email/webhook alerts for new drift, verifier failures, denied MFA challenges, agent offline transitions, and unreachable agentless nodes. Email requires a verified account and SMTP. The shared webhook destination comes from `NOTIFICATION_WEBHOOK_URL` and must use HTTPS; deliveries retry up to five times. Without a configured channel destination, pending deliveries wait for configuration.
- Administration can suspend or delete operators and revoke their sessions. Self-service password changes verify the current password and invalidate existing sessions.
- Account settings can save a system, Hacker, or Enterprise theme; a browser-only override applies immediately without changing the account preference. The Enterprise layout uses the supplied dashboard, asset, activity, and policy screenshots in `docs/` as visual references, with WinFire branding and live control-plane data.
- Enterprise is the default light theme; the top bar toggles it with the dark theme. The login page has a full-screen illustrated background.
- Vue Flow policy authoring, live port/address/program validation, connected port/address/profile scopes, local and remote port rules, immutable versions, graph and rule diff, recall, node and group assignment conflict checks, audited apply runs, read-only WinRM drift checks, and a remote PowerShell WinRM adapter. Schedule and MFA Gate nodes are rejected at compile time until their enforcement services exist.
- A classic policy table edits the same graph as the visual editor. Firewall events can create scoped allow or reject rules in a node's personal policy or an assigned group/global policy. Enforced nodes receive saved revisions only after an administrator opens **Sync policies** and starts or schedules deployment. Automatic training follows its own configured timeline. The Sync window lists pending node-policy pairs and scheduled runs.
- Rule compilation removes identical rules and combines compatible local ports, remote ports, or addresses without widening the allowed traffic. A separate two-rule IPv4 loopback baseline is queued automatically for each eligible agent node or applied over WinRM; failed attempts retry. Windows rejects an explicit IPv6 `::1` address in these firewall rules, while the event controls still recognize IPv6 loopback.
- Policy Studio lists each node and group assignment and can remove it. Agentless removal reads and clears only that policy's managed rule group, keeps the assignment if cleanup fails, and restores earlier hosts when a later host in a group fails. Overlapping assignments keep the shared policy rules. Direct agent assignments queue an empty-rule job and remain assigned until the agent confirms cleanup; failure or revocation retains the assignment for retry. Group removal that includes agent nodes still needs coordinated cleanup and is rejected.
- Inventory shows a node's group memberships and can remove an agentless node from a group. If group policies would stop covering the node, removal first clears those policy rule groups and retains membership if cleanup fails. It requires write access to the group and each affected policy. An agent node requiring policy cleanup remains a member until agent cleanup is supported.
- Clicking a group opens its member list and count. Removing a member requires confirmation because the change may remove group policies from that node.
- TCP based verifier with pass/fail/inconclusive evidence and a selectable control-plane or managed Windows peer probe location, managed deny-rule confirmation, badges on nodes and policies, coverage/inventory/DNS/compliance/verification reports with CSV/PDF exports, dashboard trends, full event search filters, and WinRM Security event pull. Inventory exports flatten model, BIOS serial, firewall service and profile state instead of including a raw facts blob.
- Administration settings control event retention and the DNS refresh interval. The hourly retention job removes expired events, and a batched DNS sweep refreshes node lookups every 15 minutes when due. DNS reports flag missing PTR records and forward or reverse mismatches.
- Firewall Events hides same-host loopback traffic by default, with a per-view toggle. Administration → Logs & DNS can ignore loopback at ingestion and set how often recurring event patterns are dictionary-compressed. Event rows and timestamps remain queryable through pattern references. A five-minute scheduler checks whether compaction is due, processes bounded batches, and continues a backlog on later passes; retention runs hourly and prunes orphaned patterns.
- Audit trail has server-side pagination, search, column sorting, filters, and CSV, PDF, and Excel-compatible XLS exports.
- Learning sessions that propose a policy version for operator review and require explicit approval before application; segment and MFA challenge records; logon-rights baseline read; C# agent enrollment, certificate renewal, revocation, queued policy jobs, and Security event shipment with a persisted cursor.
- Before an agentless host finishes automatic training, WinFire reads the Windows Filtering Platform Connection audit policy and requires success auditing. AD discovered and manually added hosts automatically enable success and failure auditing during onboarding with readback and rollback on failure. The node detail shows this state and offers a read-only recheck and a manual enable action. A disabled audit policy leaves training active with an actionable error. Group Policy can override the local setting. Success auditing can generate many Security events, especially on busy servers. [Microsoft documents this audit subcategory](https://learn.microsoft.com/en-us/windows/win32/fwp/auditing-and-logging).
- Hourly scheduled verifier and drift sweeps; adjust with `SWEEP_INTERVAL_MINUTES`. WinRM and WMI event collection start shortly after boot and repeat every two minutes by default; adjust with `LOG_POLL_INTERVAL_SECONDS` (minimum 30) and `LOG_POLL_CONCURRENCY` (default 4, maximum 20 concurrent nodes). It samples the newest Security events for a current activity view while a separate cursor backfills older records without dropping the backlog; concurrent pulls cannot move that cursor backward. The Logs page refreshes its first page every 30 seconds while visible, and its pull button can collect from managed nodes. [Filtering Platform Connection auditing](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/plan/security-best-practices/advanced-audit-policy-configuration) must be enabled on each Windows host for 5156/5157 firewall events; inspect or enable it from the node details when WinRM or authenticated WMI is available. Transient transport errors move nodes through degraded and unreachable states with retry backoff; scheduled checks retry when the backoff expires. Enrolled agent nodes receive readback jobs for drift checks; the Windows agent runtime still needs live validation.

## Windows connector requirements

The remote adapter uses Python `pywinrm` on Linux, and `pwsh` on Windows for modern hosts. Older PowerShell 2 hosts use the Python compatibility sidecar on either control-plane OS. Modern hosts call `NetSecurity` and `Get-WinEvent` on the target. The adapter needs a trusted Windows account with rights to read and manage firewall rules and read the Security log. Local Administrator on each managed host is the simplest working role; a custom scoped role needs equivalent firewall-management rights and `SeSecurityPrivilege` to read the Security log. Use a dedicated least privilege service account or gMSA scoped to the managed hosts. Do not use Domain Admin for routine access. Target WinRM, firewall rules, and PowerShell remoting must be configured by the operator. A port probe only shows an open management port; authenticated access is verified when facts are collected. HTTPS certificate validation is enabled by default; `WINRM_TLS_VERIFY=false` is available only for a controlled test host with a self-signed listener.

The app was built on Linux. WMI/DCOM facts, firewall inventory and writes, audit-policy management, and Security event reads use the authenticated ADMIN$ staging path on Vista+ hosts. Netsh-over-remote-shell fallback is **not implemented** in this build.

The single-right LSA write path has automated tests for add, no-op, remove, API authorization, readback, and audit recording. A live WinRM roundtrip on ORLANDO (`192.168.250.7`) assigned `SeBatchLogonRight` to a random synthetic SID, verified it, removed it, and verified the assignment was absent. The sidecar compresses PowerShell before sending it because the uncompressed rights script exceeded the test hosts' WS-Man command-input limit. To repeat the isolated API test on a disposable Windows host, set `WINFIRE_TEST_HOST`, `WINFIRE_TEST_USER`, and `WINFIRE_TEST_PASSWORD` in the shell environment and run `npm run test:winrm:rights:write`. It creates a temporary database and attempts cleanup on failure. Do not run it against a production domain controller.

Host facts and paged firewall-rule inventory have passed automated tests and live read-only checks on HOUSTON; the WMI rule path returned 341 rules. The PowerShell 2 compatibility path still needs a live older-OS host. LDAPS and StartTLS were unavailable on the current test endpoint, so directory sync has been verified with a mock directory only. A trusted LDAPS domain controller and read-only bind account are needed for live AD validation.

## Safety and deployment

Use HTTPS at the deployment edge and set a strict `CORS_ORIGIN` if the UI is served from another origin. The UI uses bearer tokens, not cookies. Protect the `data` directory and configure backups for the database and encryption key file. `npm start` uses one Express port for API and UI; a reverse proxy can terminate TLS on the same public origin.

Policy changes are scoped by the `WinFireSecure:<policyId>` group. Review compiled rules before applying. In Policy Studio, choose **Verify** and select either the control plane or a managed WinRM peer as the probe location. Results and the verification report record the chosen location. Peer connection errors and checks against the peer itself are inconclusive. The verifier checks for a matching managed deny rule where possible; an unreachable target or unconfirmed deny remains inconclusive because the check cannot prove which device dropped a packet.

Invitations can be created from Administration. With `SMTP_HOST`, `SMTP_FROM`, and `PUBLIC_BASE_URL` configured, the server emails a seven-day link over TLS. Without SMTP it returns a one-time link to the admin for manual delivery. The invite token is stored only as a hash and is consumed once. Manual delivery does not mark the account email as verified. SMTP delivery has not been tested against a real mail server.

Changing an account email requires SMTP: the current address stays active until a one-day verification link sent to the new address is consumed. Verification revokes existing sessions. Accounts created from manually delivered invites can request verification once SMTP is configured.

## Agent development

The agent source is in `agent/WinFire.Agent`. `npm run build:agent` publishes a self-contained Windows x64 executable. It is unsigned until an operator signs it. The installer `agent/Install-WinFireAgent.ps1` refuses unsigned binaries, enrolls with a short-lived token supplied through stdin, stores the private key in the Windows machine certificate store, and installs an auto-start Windows Service. Its `EventLogWatcher` wakes a cursor-based Security log reader; batches are acknowledged over mTLS before the cursor advances, so retries are deduplicated by node and record ID. The remote deployment action uses the same signed executable and runs the installer logic through the node's WinRM session. Agent API integration tests pass, but service installation has not run on Windows. A signed MSI, signed self-update path, and live Windows validation remain to be built.

Agent enrollment requires the Express server to run HTTPS directly. Set `TLS_CERT` and `TLS_KEY` to a server certificate and key trusted by Windows clients, and set `AGENT_CA_CERT`, `AGENT_CA_KEY`, and `AGENT_CA_PASSPHRASE` to a dedicated client-certificate CA. Production startup rejects an unencrypted agent CA key. Keep its encrypted key outside the database and container image; provide the passphrase through a secret manager. All four certificate paths must be configured together. The same Express port then serves the UI, API, and mTLS agent routes. The server requests client certificates but only agent routes require one; each agent request checks its registered certificate fingerprint and revocation state.

For a test CA, create an encrypted key and certificate outside the repository:

```bash
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -aes-256-cbc -pass env:AGENT_CA_PASSPHRASE -out /secure/agent-ca.key
openssl req -new -x509 -key /secure/agent-ca.key -passin env:AGENT_CA_PASSPHRASE -out /secure/agent-ca.crt -days 365 -subj '/CN=WinFire Agent Test CA' -addext 'basicConstraints=critical,CA:TRUE' -addext 'keyUsage=critical,keyCertSign,cRLSign'
```

The server certificate should be issued by a CA trusted on the Windows nodes. To test enrollment, create a node and token in Administration, then run the signed installer from an elevated PowerShell session with the published executable and server URL. The token expires after 15 minutes and cannot be reused. The Windows agent polls for policy jobs every 30 seconds; push, event streaming, and MFA gating are not yet implemented.
